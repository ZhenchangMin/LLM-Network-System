30–45 min轻量

LLM 到底是什么？

只建立 decoder-only Transformer 的高层心智模型：token → embedding → 多层 Transformer → next-token probability。

  • 知道 token 不是“一个单词”
  • 知道 LLM 的输出本质是逐 token 预测
  • 知道 inference 和 training 是两件不同的事
推荐：Hugging Face Transformer 入门 →
45–60 min轻量

Attention 只理解 Q / K / V

不用推完整矩阵求导。理解 Query 是“我在找什么”，Key 是“我有什么”，Value 是“真正取回的信息”。

  • 看懂 self-attention 的数据流
  • 理解 causal mask：不能看到未来 token
  • 理解为什么历史 K/V 能被重复利用
可选视频：Karpathy Attention 章节 →
30–40 min轻量

Prefill 与 Decode

这是从“懂 LLM”跨到“懂 LLM Infra”的关键。Prefill 一次处理 prompt；Decode 之后每轮通常只生成一个新 token。

  • Prefill：并行度高、计算密集
  • Decode：逐 token、经常更受内存带宽影响
  • TTFT 与 TPOT/ITL 分别对应不同体验
推荐：NVIDIA Inference Optimization →
45 min核心

KV Cache：项目真正的起点

生成第 n+1 个 token 时，不应该重新计算前 n 个 token 的 K/V。缓存它们，用显存换计算。

  • 为什么 KV Cache 会随 sequence length 增长
  • 为什么长上下文 + 高并发容易吃满显存
  • 为什么 cache 管理直接影响吞吐和延迟
必看：Hugging Face KV Cache →
60–75 min核心

PagedAttention：把 OS 知识迁移过来

你们学过虚拟内存，这是最大的优势。vLLM 把 KV Cache 分成 block，思路和 paging 很相似：避免连续大块内存带来的 fragmentation。

  • physical block / logical block 的对应关系
  • internal / external fragmentation
  • 为什么更好的内存利用率能容纳更大的 batch
论文只读图 + Introduction + Design →
45–60 min适中

Prefix Caching：不同请求也能复用 KV

如果多个请求共享 system prompt、长文档或对话前缀，之前算过的 KV 可能直接命中，而不是重新 prefill。

  • 区分“同一次生成的 KV Cache”和“跨请求 Prefix Cache”
  • 理解 hash / radix tree 两类组织思路
  • 理解 hit rate 为什么与 workload 强相关

45–60 min核心

Cache 满了：Evict、Offload 还是保留？

这就是你们最可能产生方法创新的位置。显存有限时，需要决定“谁值得继续留在快层”。

  • LRU：最近最少使用
  • ARC / frequency / reuse：考虑访问模式
  • GPU → CPU：容量变大，但搬运也有代价
必看：vLLM KV Offloading →
30–45 min适中

最后学会读实验指标

系统优化不能只说“更快”。至少能区分用户体验指标、吞吐指标和 cache 指标。

  • TTFT：请求到第一个 token
  • TPOT / ITL：后续 token 的生成节奏
  • Throughput：tokens/s 或 requests/s
  • Cache hit / eviction / preemption：解释为什么快或慢

MENTAL MODELS

把新知识挂到你们学过的课上

LLM Infra 不需要从零建立一套完全陌生的知识。很多核心问题其实就是 OS / Architecture 在新的 workload 上重新出现。

操作系统→PagedAttention

虚拟内存 / Page

KV Cache 不再要求每条 sequence 占一整块连续显存，而是拆成固定大小的 block。重点关注 fragmentation、mapping、sharing。

Cache→KV Eviction

LRU / Locality

当容量不够，决定淘汰谁。传统 recency 只是一个信号；LLM workload 还能利用 prefix reuse、recompute cost、session state 等信息。

存储层次→KV Offload

HBM ↔ DRAM ↔ 更慢介质

GPU HBM 快而小，CPU RAM 慢而大。把 KV 搬出去能腾显存，但要支付传输和恢复的延迟。

排队 / 调度→LLM Serving

吞吐 vs. 尾延迟

更大的 batch 常有利于吞吐，却可能增加等待。系统优化必须说明是在优化 throughput、TTFT 还是 tail latency。

PROJECT 5 LENS

学完以后，应该能回答这些问题

如果组员能独立回答下面大部分问题，就已经具备开始做 baseline、profiling 和 policy design 的共同语言。

1. KV Cache 到底缓存了什么？为什么只在 inference 中特别重要？

每一层 self-attention 对历史 token 计算出的 Key / Value。自回归生成时历史 token 不会变化，因此可以复用；代价是 cache 随上下文增长而占用大量显存。

2. 为什么“显存更省”会提高 serving throughput？

更少的 KV 内存浪费通常意味着同一张 GPU 可以同时容纳更多 active sequences，从而形成更大的有效 batch，提高硬件利用率。但这不是无条件成立，仍需实测延迟与吞吐。

3. Prefix Cache 和单个 request 的 KV Cache 是一回事吗？

底层存的仍是 KV，但复用范围不同。普通生成 cache 主要避免同一 request 内重复计算；prefix caching 进一步尝试跨请求复用相同前缀对应的 KV block。

4. Cache 满了为什么不能无脑 LRU？

“多久没访问”不一定等价于“以后没价值”。某个很久没访问的 session 可能正在等待 tool，很快就会恢复；某个最近访问的大 prefix 也可能是一锤子买卖。Project 5 的研究空间就来自这些 workload-specific signals。

5. CPU Offload 为什么不是免费的额外显存？

GPU HBM 与 CPU DRAM 之间需要搬运数据。若 cache reuse 的计算节省不足以覆盖传输、同步和管理开销，offload 可能反而变慢。

6. 我们最终至少要测哪些指标？

TTFT、TPOT/ITL、throughput 是服务质量基础；同时记录 cache hit/miss、eviction、GPU KV utilization、preemption/offload 行为，才能解释性能变化的原因。

CURRENT DIRECTION

从“更聪明的淘汰策略”开始，而不是重写整个 inference engine

推荐先把 LRU / ARC 当 baseline，再探索 workload-aware、queue-aware 或 session-aware 的 cache value。这样既有清晰研究问题，又能利用现成 vLLM 基础设施控制工程风险。
