# Agent Session 与 PEEK 缓存保留：启发式探索记录

> 2026-11-02。**这是独立探索，不是 A/B/C 组的正式交付，也不是 SGLang/PEEK 的论文复现实验。**

## 研究问题

PEEK Online 利用当前等待队列（Pending Radix Tree）中的共享前缀需求进行 cLPM 调度和 Queue-aware Eviction。但 Agent 在工具调用期间可能暂时**不在模型等待队列**，之后又以相同上下文继续推理。我们希望知道：

- 工具调用间隔内，多少一次性请求会驱逐待续 Agent 的前缀？
- 若额外允许缓存策略获得“Session 正在等待工具结果”的信息，能否减少下一轮重新 Prefill？
- **若工具调用最终没有继续**，提前保留这些前缀会不会损害其他任务？

**代码核对：** PEEK 官方 `python/peek/online/eviction.py` 已有 `plain`、`cluster`、`recency`、`decay` 四类分数。PEEK 默认 cluster 模式利用当前队列的祖先需求数量和前缀长度。**增加衰减本身并非创新点**；这次探索的是队列之外的 *pending-tool-session* 信号，不能将它直接视作已经证明的新方法。

## 实验一：真实 SGLang RadixCache 的 CPU 模拟

位置：贝叶斯云 `/root/bayes-tmp/peek-exploratory/`。

- 直接调用 **SGLang 0.5.9 `RadixCache.create_simulated` 和原生 LRU**，不是从零手写的假缓存。
- Agent 共享前缀 1,024 Token，下一轮更换 32 Token 尾部；中间插入 640-Token 的一次性请求。
- 分别指定 Token Cache 预算 3,072 / 4,096 / 6,144 / 8,192；共 40 组条件。
- **在没有竞争时：** 下一轮命中 1,024 Token；在对应容量下，4 / 5 / 8 / 12 个一次性请求足以将其降为 **0 Token 命中**。

解释：有明确的缓存竞争边界，但**这只是容量受限下 LRU 的合理行为，不是 PEEK 缺陷证据**。无 GPU、无真实推理、无请求调度和服务时延测量；CPU 模拟使用合成 Token IDs。

## 实验二：暂停 Session 信息是否有帮助？

本目录包含可执行的纯 Python 抽象模拟：

- `paused_agent_probe.py`：标准库实现，不依赖 GPU；每次模拟 Cache 容量 3,200 Token 单位，三个初始前缀 A/B/C（长度 1,280 / 512 / 768），再加入 2/4/6 个 640-Token 一次性前缀。
- 比较三类**代理策略**：`LRU`；`queue`（优先保留当前等待请求依赖的前缀，用作 PEEK 队列信号的概念代理）；`pause+queue`（队列信号 + 当前处于工具等待中的 Agent A 的保护加分）。
- **注意：`queue` 不是 PEEK 的真实实现**，`pause+queue` 也不是已实现的 Extension。此模型将前缀按独立缓存对象计费，不模拟真实 Radix Tree 的拆分、锁定、祖先节点和混合服务。
- Agent A 的实际返回概率设为 **95%、50%、5%**（仅用于产生未来事件；策略本身不直接读取概率）。还枚举保护 TTL、请求噪音量及保护权重。
- 固定 24 个独立种子，每个种子 300 个独立 Episode，策略之间严格复用同一组请求时间线。下面是噪音=4、TTL=8 个模拟 tick、保护权重=0.5 的结果。

| Agent 实际返回概率 | 只看等待队列：平均 Miss Tokens/Episode | 等待队列 + 暂停 Session | 变化 |
|---|---:|---:|---:|
| 95% | 3,919.9 | 3,824.0 | **−2.45%** |
| 50% | 3,345.2 | 3,824.0 | **+14.31%** |
| 5% | 2,771.8 | 3,824.0 | **+37.96%** |

在本构造中，额外的 Agent 保护提高了低价值 Session 的存活率，也可能挤出 B/C 前缀。保护信号过期时间很短时，帮助有限；保护时间太长且工具调用不返回时，劣化明显。测试了 0.10 / 0.25 / 0.50 / 1.00 / 2.00 的保护权重，该示例的主要方向一致，但这反映了当前简化负载的离散选择结构，不代表真实系统中权重不重要。

**如何理解结果：** 这是为了寻找能**证伪** Extension 方向的反例，而不是模型准确率、TTFT 或 PEEK 的真实相对收益。多数设定被我们人为指定，不能泛化为实际 Agent 的返回率分布。任何后续策略必须做时间/容量/负载及无共享场景的对照。

## 对 C 组可能有价值的研究假设（不指定其必须采用）

- **H1：可观测 Session 状态提供增量信息。** 一个暂停中的 Agent 不会自动出现在 PEEK 的等待队列中；如外部工具能够以较低开销提供活跃状态/可信超时标志，可能保留跨轮高复用前缀。
- **H2：错误保护比不保护更危险。** 对不会返回的 Session 持久保留缓存，会挤占正在等待的真正需求，严重时比只看队列更差。
- **H3：保护必须受可信度、TTL 和内存压力共同约束。** 简单“所有暂停 Agent 加固定优先级”不足以作为有说服力的 Extension。
- **对照要求：** 不仅比较 PE vs 改进，还必须和 Vanilla LRU、PEEK 官方 `recency/decay` 等已有变体比较，避免重复已有工作。

**当前结论：** 跨轮 Session 信号值得进一步测试，但它是否有价值取决于其**可获得性与可靠性**；尚不能认定它是有效的 PEEK Extension。
